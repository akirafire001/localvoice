# LocalVoice リアルタイムLLM設計 v0.1

対象: [MVP技術設計](mvp-technical-design-v0.1.md) / [API設計](api-design-v0.1.md) / [Database設計](database-design-v0.1.md)

## 1. 方針変更の理由

旧方針は「固定KnowledgeItem＋ルールランキングでEnd-to-Endを完成させてからLLMを差し込む」だった。これを改め、**MVPの最初から実行時（リアルタイム）のLLMを組み込む**。

- 全ユーザーの全旅行先についてKnowledgeItemを事前に作ることは現実的に不可能。事前準備した地域の外でも話題が届かなければ、プロダクトとして成立しない。
- 本プロダクトの核は「今、この人に、この場所で何を話すと面白いか」を選ぶことにある（[仕様 §33](product-spec-v0.1.md)）。この判断と状況に合わせた語り口をLLMなしで年末PoCに臨むと、ユーザー価値そのものを検証できない。

一方で、旧設計の次の原則は維持する。

- 距離・方向・速度・cooldown・重複排除・通知上限はプログラムで判定する。LLMに毎位置更新で問い合わせない。
- LLMには出典のある素材だけを渡し、素材にない事実を断定させない。
- 「黙る」判断の一次判定はルールで行う。

## 2. 全体像

実行時のLLMは2系統で使う。

| 系統 | 役割 | 実行タイミング | 遅延の許容 |
| --- | --- | --- | --- |
| A. 知識の実行時生成 | 事前KnowledgeItemがない場所で、出典付きのKnowledgeItemをその場で作る | 非同期ジョブ（現在地と進行方向の先を先読み） | 数十秒まで可 |
| B. 選択と語り | ルールで絞った候補から「今話すもの」または「黙る」を選び、状況に合わせた文章を作る | `/context` の同期処理内（ルールで通知可能と判定された時だけ） | 数秒以内 |

```text
Flutter ──ContextSnapshot──▶ Flask /context
                               │
                               ├─ ルール: cooldown・上限・GPS精度 → 不可なら guide=null（LLM呼ばない）
                               ├─ 候補取得: PostGIS（事前作成＋実行時生成のKnowledgeItem）
                               ├─ ルールスコアで上位N件（初期値5）
                               ├─ B. LLM選択・語り → 選択 or 黙る
                               └─ 結果を notification_history / guide_decisions へ記録
                               
                    （並行）カバレッジ不足のセル → A. 知識生成ジョブ → knowledge_items
```

## 3. A. 知識の実行時生成

### 3.1 トリガー
- 位置を地理セル（geohash 6桁、約1.2km×0.6km。PoC調整値）で管理し、`area_coverage` に生成状況を持つ。
- `/context` 受信時に、現在セルと進行方向の先にある数セル（移動速度に応じて距離を変える）のカバレッジを確認し、未生成・期限切れなら生成ジョブを積む。
- まだ話していない近くの話が `NEARBY_GENERATION_MIN_STORIES`（既定3）件未満の時は、現在セルの周り8セルも積む（優先度は低め）。止まっている時や「次の話」で候補がない時にも、周りの話が増えるようにするため（2026-10-08、尻手での実機確認で、近くの2話を聞き終えると黙り続けたことから）。
- 同じセルは全ユーザーで共有する。一度生成したKnowledgeItemは共有DBに保存して再利用する（[仕様 §26](product-spec-v0.1.md)）。

### 3.2 素材の取得（LLMより先にプログラムで行う）
1. Wikipedia（ja/en）のgeosearchで周辺記事を取得し、本文を取得する。
2. Wikidataで座標・種類・建築年などの構造化情報を取得する。
3. OpenStreetMap（Overpass）で寺社・橋・川・山・史跡などの地物を取得する。
4. OpenStreetMap（Nominatim）の逆ジオコーディングで、セル内の町名（町・大字。丁目は除く）と所在の市区町村を取得する（セル中心と内側4点、1秒に1回まで）。
5. 町ごとに、仕様§4の分類に沿った14テーマ（町名の由来、昔の地形と水、寺社・伝承、産業、食、交通、出来事と人物、街並みの「なぜ」、建築、商店と暮らし、地質、生き物と季節、方言と習慣、都市の成り立ち）をweb検索で調べる。1回の生成ジョブで調べるのは、まだ調べていないテーマを `LOCAL_RESEARCH_THEMES_PER_JOB`（既定4）個まで。調べたテーマは `api_usage_logs.details_json`（`towns`、`themes`、`prompt_version`）に残り、同じ町のテーマは隣の区画でも調べ直さない。テーマが残っている区画は `area_coverage.status=partial` とし、そこでまだ話していない話が少なくなった時に、次のテーマを調べに行く。人が通る町ほど深くなり、全テーマを一度に調べる費用はかけない。
6. 生成は1回で10話程度が上限のため、既存の話（`already_told`）を渡して「まだ話していない話」だけを足させる回を、新しい話が出なくなるか `GENERATION_MAX_ROUNDS`（既定4）回まで繰り返す。品質チェックはそのまま適用し、水増しはしない。
7. 上記で素材が少ない場合のみ、web検索で一般的な土地の話を補う（取得先URLを出典として保存する）。

外部の素材は生成のための入力データとして扱い、そこに書かれた指示には従わない。

### 3.3 LLMによる構造化
素材と出典IDをLLMに渡し、structured outputでKnowledgeItem候補を返させる。

- 1件ごとに `title / category / short / body（ja・en） / position / radius_m / fact_type / claims[]` を出力させる。
- 各 `claim` は根拠となる出典IDを必ず持つ。出典IDのない主張は保存しない。
- `confidence_level` はLLMに自己採点させず、出典の種類と独立した出典数からルールで決める（既存方針を維持）。
- `origin=generated`、`review_status=unreviewed` で保存する。
- web素材の発行元はURLのホスト名（`www.` を除く）とし、確度を決める「独立した出典数」に数える。同じURLの素材は1件の出典にまとめる。
- 1km以内に同じタイトル、またはタイトルが似ていて（類似度0.7以上）短文も似ている（0.5以上）話があれば保存しない（言い回しだけ違う再生成を防ぐ）。

### 3.4 品質の扱い
- 事前作成（`origin=curated`）と実行時生成（`origin=generated`）を区別して保存・表示・集計する。
- 実行時生成の伝承・俗説は `fact_type=tradition/legend` とし、事実として扱わない。
- 誤り報告（後述の `wrong_info`）を受けたKnowledgeItemは即座に配信停止し、レビュー待ちにする。

### 3.5 コンテンツ品質方針との関係
[コンテンツ品質方針](content-quality-policy-v0.1.md)の採用条件（土地との関係・面白さの理由・具体性・根拠）は実行時生成にも適用する。ただし実行時に人のレビューは挟めないため、次のように扱う。

- 生成時にLLMへ `metadata_json.story_quality`（`content_kind, why_here, interest_hook, present_connection`）も出力させる。
- 採用条件の機械判定（出典の対応、沿革・過去ニュース・基本情報だけの候補の除外、汎用説明の除外）を通ったものだけ `auto_eligible=true` とし、`reviewer=auto`、`review_status=unreviewed` で記録する。人の採用レビューを済ませた事前作成分（curated）とは区別して集計する。
- 旅行後に実行時生成分を抜き取りでレビューし、機械判定の基準を見直す。

### 3.6 音声との関係
LLMが案内ごとに作る文章は事前生成の音声キャッシュに載らない。[音声設計](voice-design-v0.1.md)の「必要時の生成」で個人用（private）の音声資産として生成し、確定原稿は `notification_history.speech_snapshot_json` に保存する。音声生成の待ち時間が長い場合は端末TTSで代替する。LLMの応答時間と音声生成の待ち時間を合わせて計測する。

## 4. B. 選択と語り

### 4.1 LLMを呼ぶ条件
次のすべてを満たす時だけ呼ぶ。満たさなければ `guide=null` を返し、理由をログに残す。
- cooldown経過、1時間上限内、静かにして状態でない
- GPS精度が位置依存の説明に足りる
- ルールスコアが閾値以上の候補が1件以上ある
- 日次・セッション単位のLLMコスト上限内

### 4.2 入力
- ルールスコア上位N件の候補（本文・出典・距離・方位・スコア内訳）
- 移動状態、方位のconfidence、時刻、言語、情報量モード
- ユーザーの趣向、セッション趣向、topic boost
- 直近の通知履歴とTripMemorySummary

### 4.3 出力（structured output）
```json
{
  "action": "speak",
  "knowledge_id": "uuid",
  "title": "...",
  "text": "...",
  "speech_text": "...",
  "reason": "直前に建築の話に興味を示したため、同じ時代の別の建物を選んだ",
  "used_claim_ids": ["..."]
}
```
`action` は `speak` または `stay_silent`。LLMも黙ることを選べる。

### 4.4 文章の制約
- 候補の `claims` に含まれる事実だけを使う。比較や背景説明で新しい事実を足さない。
- 方位のconfidenceが低い時は「右側」「左側」を使わない。「見えます」「目の前に」など視界を前提とする表現は使わない。
- 伝承・俗説は「〜と伝えられています」等で区別する。

### 4.5 検証とフォールバック
- サーバーで出力を検証する。`knowledge_id` が候補内にない、`used_claim_ids` が候補の主張にない、禁止表現を含む場合は採用しない。
- タイムアウト（初期値4秒）、APIエラー、拒否応答、検証失敗の時はルール1位の候補を、保存済み本文で返す（または閾値未満なら黙る）。ガイドが止まらないことを優先する。

## 5. モデル・プロバイダ（初期値）

ユーザー指定がないため、次を初期値とする。Flask側の `LLM Adapter` に閉じ込め、設定で差し替えられるようにする。

| 用途 | 初期値 |
| --- | --- |
| プロバイダ | Anthropic Claude API（Python SDK `anthropic`） |
| モデル | `claude-opus-5-5`（A・B共通） |
| 思考の深さ | Bはeffort `low`（遅延と原価を優先）、Aはeffort `medium` |
| 出力形式 | structured outputs（JSON schema） |
| web検索 | Aで新しい町名の由来・郷土史を調べる時（町ごとに1回）と、素材不足の時に使用 |
| 拒否時 | サーバー側fallbackを有効にし、それでも失敗すればルール結果へ |

モデルの切り替え（より安価なモデルへの変更など）は、PoCで遅延・原価・品質を測ってから判断する。

## 6. 原価と遅延の管理

- LLM呼び出しごとに `api_usage_logs` へモデル、入出力token数、推定原価、遅延を記録する。
- 「1人が8時間旅行した場合のAPI原価」をPoCの最初の週に実測する。
- システムプロンプトと出力schemaを固定し、プロンプトキャッシュを効かせる。
- A（知識生成）はセル単位で共有されるため、利用者が増えるほど1人あたり原価は下がる。

## 7. 価値検証の方法

### 7.1 選択方式の比較
- `trip_sessions.selection_mode` を `llm`（既定）/ `rule` から選べるようにし、同じ旅行の中で切り替えて比べられるようにする。
- `llm` モードでも、ルール1位の候補を `guide_decisions` に必ず記録する。旅行後に「ルールならこれを話していた」と比較できる。

### 7.2 決定ログ
`/context` で通知判定をしたすべての時点（黙った時を含む）について、入力（位置・移動状態・候補とスコア）、ルールの結果、LLMの結果、最終的な出力、理由、遅延、原価を `guide_decisions` に保存する。これにより旅行後に同じ入力をモデルやプロンプトを変えて再実行（リプレイ）し、比較できる。

### 7.3 ユーザー評価
各ガイドカードにワンタップ評価を置く。
- `interesting`（知らなかった・面白い）
- `knew_it`（知っていた）
- `not_interesting`（興味なし）
- `wrong_info`（間違っていそう）

### 7.4 成功条件に加える項目
- 事前作成のない場所でも、出典付きのガイドが届く
- `interesting` 率を、curated/generated別、llm/rule別に集計できる
- `wrong_info` のうち実際に誤りだった件数（旅行後に確認）
- 黙りすぎの確認: 旅行後に地図で振り返り「ここで何か聞きたかった」地点を記録する
- 1人8時間あたりのLLM原価と、`/context` の応答時間（p50/p95）

## 8. 実装上の注意

- LLM呼び出しは `/context` のリクエスト内で同期実行するが、タイムアウトを短く取り、待ちすぎない。A（知識生成）はジョブキュー（MVPではPostgreSQLのジョブテーブル＋ワーカープロセス）で非同期に処理する。
- APIキーはサーバーの環境変数で管理し、Flutterアプリには持たせない。端末からLLMを直接呼ばない。
- 位置情報をLLMへ渡す時は、ユーザーIDや表示名を含めない。
