## 2回目レビューで特に再確認した技術制約

### Android

- Android 10以降はバックグラウンド位置利用時に `ACCESS_BACKGROUND_LOCATION` が関係する。
- Android 11以降では「常に許可」は通常の権限ダイアログではなく設定画面側でユーザーが許可する流れ。
- Google Playはバックグラウンド位置情報をコア機能に必要なケースへ制限している。
- Android 8以降では通常バックグラウンド実行時の位置更新頻度に制限がある。
- foreground serviceとして位置を扱う方式も含め、旅行セッション中の実装をPoCで比較する。

**結論:** 常時監視ではなく、ユーザーが明示的に「旅行ガイド開始」したセッション中だけ追跡する。

### iOS

- Core Locationでバックグラウンド位置更新は可能。
- Background Modes/location設定が必要。
- 継続的な高精度位置取得は電池消費につながるため、速度・状態に応じてaccuracy/distance filterを調整する。

**結論:** Androidと同じくセッション方式とし、停止中は更新頻度を落とす。

### PostGIS

`ST_DWithin` は「現在地から半径N m」の検索に適しており、空間インデックスを利用できる。LocalVoiceの速度別探索半径と相性がよい。

**結論:** PostGISをMVPから採用する。

### OSM/Nominatim

公開Nominatimは大量・系統的POI収集サービスとして使えない。重い利用には制限があり、結果キャッシュも要求される。

**結論:** Knowledge DB構築のために公開Nominatimへ大量問い合わせする設計は禁止。OSM extract、自前環境、または商用Providerを用途別に選ぶ。

## 2回レビュー後の最終判断

33項目を再点検した結果、**中核仕様に技術的に不可能なものはない**。

ただし次は「実装可能」だけでは採用判定できない。

1. 通知タイミングと通知量
2. GPSからの移動手段・方向推定精度
3. 移動先読み
4. ユーザーにとっての「面白さ」の判定
5. バックグラウンド位置取得時の電池消費
6. 1旅行あたりの外部API原価

これらは年末PoCの実機試験項目とする。

## 次工程で必要な実機検証

設計レビュー2回は完了したが、次の段階では実装後に最低以下を自動/実機テストする。

- Android/iOSで1時間以上のバックグラウンド移動
- 徒歩→停止→電車/車相当速度→停止の状態遷移
- GPS誤差時の誤通知
- 同一KnowledgeItemの重複通知防止
- topic boostの時間減衰
- 一時状態TTL
- 日英切替
- 土地の小話の量・種類・面白さ、沿革だけ/関連の薄い古いニュースの保留
- 日英TTSの同一原稿比較、地名の読み、長時間の聞き心地、原稿の欠落/追加
- 音声キャッシュ、停止後の遅着、通信断時の代替、アカウント切替・削除
- オフライン/通信断時の劣化動作
- Provider API失敗時のfallback
- 8時間旅行を模したAPI原価シミュレーション
- バッテリー消費計測

この実機検証を通過して初めて「実装方式が実証済み」と扱う。

## 2026-10-06 体験品質の仕様更新

利用者はRoadWhisper試用で学校の成り立ち・古いニュースが面白くなく、音声もiPhone標準読み上げのように感じたと報告した。この観察を[コンテンツ品質方針](content-quality-policy-v0.1.md)と[音声設計](voice-design-v0.1.md)へ反映した。競合の内部実装や全地域の品質は未検証。

Googleの現行モデル・料金、CoeFont、VOICEVOX、Kokoroの公式資料を確認し、設計文書間の端末TTS優先方針を更新した。この品質方針更新の時点では実際の音声生成・試聴・API接続・商用契約確認は未実施で、採用声/Providerも未決定だった。後続の採用決定は次節に記録する。

## 2026-10-06 MVPのTTS採用決定

ユーザーの決定により、Google Cloud Text-to-SpeechのChirp 3 HDをMVPの通常TTSとして採用する。日本語・英語の具体的な声は同サービス内の比較試聴後に確定し、日本語3声程度を目安に標準声と少数の追加声を運営が選定する。他サービスは統一比較表に将来候補として残す。

製品仕様・MVP技術設計・音声設計・API/DB・Flutter UX・実現性検討・READMEを更新した。サーバー側のGoogle Cloud認証、通常のテキスト合成によるMP3生成、事前生成・キャッシュ、必要時の個別生成、原価上限、端末TTS/文字への代替を設計へ反映した。SSML/音声制御のPreview機能はMVP必須にしない。月100万文字の仮定試算は[生成量・原価試算](tts-volume-estimate-v0.1.md)に残す。

これは仕様上の採用確定であり、API接続・音声生成・試聴・実機検証の完了を意味しない。具体的な声ID、Cloudプロジェクトの認証・請求設定、運用予算、日英の音質と地名の読みは実装・PoCで確認する。
